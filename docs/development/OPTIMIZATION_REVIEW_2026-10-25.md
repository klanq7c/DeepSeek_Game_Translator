## 范围与证据

对象为当前工作区，包含尚未提交的既有改动。检查了共享核心、C/C# 服务端、
启动器、四引擎运行时、构建与相关测试入口。本轮只新增审查记录和本地合成探针，
没有修改产品代码、配置、翻译记忆或游戏文件，也没有启动或停止用户服务。

结论分为“已复现”“调用链确认”“需实机测量”。调用链证明有额外工作或等待，
不等于已测得游戏卡顿；没有宣称具体提速比例，也不把旧构建成绩当成本轮验证。

下文的 Module 指拥有完整行为与状态的模块；Interface 包括其调用约束，
Adapter 指引擎或平台适配实现。优化应改善 Locality（同一行为集中维护），
并让测试与真实调用跨越同一个 Seam，避免只拆文件却增加调用者必须知道的规则。

## 第一批：收益依据较明确

### 1. 审计标记规则与引擎规则同步

- 文件：[审计脚本](../../scripts/audit_game_translation.ps1)，第 213、281–294 行；
  [Unity Mono](../../payloads/UnityTranslator/src/DeepSeekTranslator.cs)，第 7733 行；
  [TMP 标签解析](../../payloads/UnityTranslator/src/TmpRichText.cs)。
- **已复现**：从生产脚本 AST 提取实际 `Get-MarkerSignature` 与正则，Unity 分支
  对下列三种变化均未报告差异：`<link="quest>original">` 改成
  `<link="quest>changed">`；红绿标签序列交换；`Score: {0}` 的 `{0}` 丢失。
  保留完整链接属性的正常翻译同样不报警，作为对照。
- 原因是通用正则在带引号的 `>` 处提前结束、不识别数字格式字段，并在比较前排序。
  运行时已有完整标签边界与顺序比较，审计仍有独立规则。这是审计漏检，
  不代表这些译文一定进入运行时或导致崩溃；标签重排仍应是人工复核疑点。
- 建议：让每个引擎的标记 Module 拥有自己的规则；审计通过 Adapter 复用可共享的
  纯解析行为，并保留审计与显示接受策略的区别。不得把四种语法合并成一个正则，
  也不得因此自动改写缓存。
- 验证：扩充 `tests/launcher_parity/test_game_audit.ps1` 的精确疑点键集合，
  覆盖引号、标签顺序、数字字段、普通括号文本；同时保护已有 Ren'Py 与 RPG Maker。

### 2. RPG Maker 图片文字减少空闲帧遍历

- **已复现访问次数**：生产模块接收一个 2048 节点、没有图片翻译目标的合成场景。

- `updateScene` 每帧调用模块；模块先遍历并创建集合，再检查 `dirty`、目标变化和
  `cacheEpoch`。已有机制避免重复绘制，但尚未避免这部分发现开销。
- 建议：图片显示 Module 统一拥有目标登记、可见性变化和失效状态，结合生命周期
  更新与有界补扫。仅将 `dirty` 判断提前会漏掉同场景新目标，不能这样简化。
- 验证：在 `test_rpgm_auto_image_text.js` 增加空闲访问次数约束，并保留动态添加、
  隐藏转可见、bitmap 替换、图片/字体/缓存晚到、离场释放和原图不变断言。

### 3. C# 批量实时请求统一待发预算

- 文件：[Program.cs](../../native/src/server_cs/Program.cs)，第 252、446、523 行；
  [Api.cs](../../native/src/server_cs/Api.cs)，第 346、509 行；
  [C 实时工作池](../../native/src/server/http.c)，第 1021 行。
- **调用链确认**：多文本请求为全部分块创建任务，先生成请求体，再等 `apiGate`。
  这条路径没有使用单条实时请求的 `liveMemoryBytes` 和 32 MiB 预算，C 侧则统一
  经过实时工作池。单次请求仍受 2 MiB、服务端仍受 128 个连接和远端并发限制，
  问题是缺少统一的待发任务/提示词内存预算，并非无限并发。
- 建议：由同一实时调度 Module 管理单条与批量的准入、预算、完成与失败释放。
  保留结果顺序、去重、前台优先和关停语义，提高 C/C# 行为维护的 Locality。
- 验证：用临时假 provider 暂停响应，提交多个大批次，核对峰值待发量、远端并发、
  健康状态计数、失败/关停释放、结果顺序与两版契约。尚未测量实际内存峰值。

## 第二批：兼容性收益明确，实施需要更强守卫

### 6. Ren'Py 将译文完成与相关 Text 的刷新关联

- 文件：[Ren'Py hook](../../payloads/RenPy/iron_deepseek.rpy)，第 220、234、997 行。
- **调用链确认**：刷新通知已合并到主线程，但执行时会使 WeakSet 中所有仍存活的
  Text 失效并重启交互，没有按完成的翻译键区分。弱引用解决对象保留问题，
  不能避免隐藏或历史对象仍存活时一起重新布局。
- 建议：刷新 Module 记录文本依赖与完成键，集中维护对象生命周期，只使相关对象
  失效；无法定位依赖的情况需要有诊断依据的兼容处理。
- 验证：`test_renpy_engine_runtime.py`、`test_renpy_poll_batch.py` 及旧版主线程
  刷新守卫；增加相关/无关对象失效计数，检查动态插值、颜色动画、rollback、
  历史页重开、多个 worker 完成合并和没有 `invoke_in_main_thread` 的版本。

### 7. Ren'Py 字体覆盖保留游戏自己的分段字体

- 文件：[Ren'Py hook](../../payloads/RenPy/iron_deepseek.rpy)，第 896–945 行。
- **覆盖行为确认，具体故障未复现**：当前统一设置全部样式字体，并将枚举的
  TTF/OTF 映射到 CJK 字体，可能影响 FontGroup、emoji、符号和游戏已有映射。
- 建议：字体 Adapter 协调样式字体和全局替换表，保留 FontGroup 范围/remap 与
  特殊字形来源，再补中文覆盖。只跳过样式赋值仍可能被全局 replacement map 覆盖。
- 验证：真实 Ren'Py 7/8 的中文、符号、内联字体、语言切换与既有替换表夹具。
  这是单独的渲染兼容项目，不应并入共享译文清洗。

## 先测量再决定的候选

1. **C 缓存导出锁范围**：[cache.c](../../native/src/server/cache.c) 第 361、379 行
   在读锁内完成遍历、JSON 转义和扩容，会推迟写锁获得。C# 已先快照再序列化。
   先用拥有的 1 万/10 万条临时缓存测导出并发写入的尾延迟和峰值内存；C 的快照
   必须拥有有效字符串，不能照搬托管引用，也不能损害一致导出与持久化契约。
2. **Unity/RPG Maker 启动前预热**：[ui.c](../../native/src/launcher/ui.c) 第 2054 行、
   [LaunchFlow.cs](../../native/src/launcher_cs/LaunchFlow.cs) 第 105 行先预热再启动。
   先测已有译文导入、资源扫描、排队各阶段耗时；再考虑保留导入前置、扫描后台化。
   验证首屏命中率、导入/启动次序、C/C# 请求体与资源读取竞争。
3. **Unity Mono 可选深预取预算**：[DeepSeekTranslator.cs](../../payloads/UnityTranslator/src/DeepSeekTranslator.cs)
   第 2201 行只把新处理对象计入预算，已扫描对象仍可能全量枚举检查；第 8685 行
   集合达到容量后清空。该功能默认关闭，实时繁忙时已有避让，优先级较低。
   应分别衡量发现、检查、新处理的数量；游标本身不能消除全量发现 API 的成本。
4. **HTTP 分片解析**：[http.c](../../native/src/server/http.c) 第 1548 行及
   [Program.cs](../../native/src/server_cs/Program.cs) 第 907 行存在重复头部扫描/
   转字符串。增量状态有望减少大量分片时的工作，但 localhost 短请求收益可能很小。
   必须保留跨块分隔符、非法长度、大小上限和超时契约。

## 保留的设计与验证边界

已有本地缓存优先、实时通道保留、批量落盘、Godot 分片扫描与单次文本计划、
Unity 同步扫描快照、启动器绘图缓冲均有明确用途。C/C# 镜像和跨引擎守卫也应保留。
本轮没有找到足够依据去重写 Godot 或 IL2CPP 的这些路径。

Unity Mono 文件较大，但单纯拆文件没有足够收益依据。可在上面具体行为改进时，
把状态与规则一起移入对应 Module，让测试直接覆盖实际 Interface；逐步减少
`generate_seams.py` 对私有方法抽取与手写替身的依赖，继续保留真实调用链守卫。

本轮执行了生产模块的图片空闲扫描计数探针、生产审计函数的四个合成样例。
原始探针和日志位于本地 `.scratch/optimization-review-2026-10-25/`。
没有重跑完整构建，没有调用真实 provider，也没有进行四引擎实机性能测试。
建议先完成第一批，每次只改变一个行为，再按相应契约和相邻引擎守卫验证。
