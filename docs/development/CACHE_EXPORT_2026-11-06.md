# 0.4.1.1 缓存导出锁范围（2026-11-06）

## 范围与决定

继续优化审查中“先测量再决定”的第 1 个候选。影响范围是四引擎共用的本地 C 服务缓存，
只改变完整 map/entries 导出的内部实现。HTTP 路由、响应字段、单键查询、译文归一化、
持久化、C# 服务行为和用户配置保持原样。C# 原有 Snapshot 已在锁内取得不可变字符串引用。

本次采用有所有权的快照缩短写入等待。它增加临时内存与总导出耗时，是并发响应性的取舍，
不是整体提速或省内存。没有真实游戏 FPS、网络请求耗时或真实提供商性能结论。

## 复现与方案

旧 C 实现持有缓存读锁遍历、JSON 转义和输出扩容，写者一直等到编码完成。
源链接真实 cache.c、buf.c、util.c、b64.c 的探针，在导出取得读锁后通知独立线程更新已有键；
测量整个写入、独占锁等待、读锁占用、导出耗时和进程内存，不使用网络或用户缓存。

先区分三个原因：

1. JSON 编码占用读锁：若它主导等待，锁外编码应缩短并发写入延迟。
2. 输出扩容占用读锁：预留输出容量的旧实现对照能分离这部分成本。
3. 遍历和复制本身成本：快照仍需 O(N) 工作，应同时测量剩余锁占用、总耗时和峰值内存。

预留容量的旧实现仍有明显阻塞；它没有消除编码占锁。新实现 cache_export_snapshot
在同一次读锁内精确计算总字节并复制所有 NUL 结尾的键、值，保留原桶遍历顺序。
释放锁后才做 JSON 编码，最终释放快照。不能只复制表内指针：并发覆盖会释放旧值，
扩容也会释放旧桶数组。计数与键值属于同一快照。

快照只有一块按实际字节分配的内存，不做每条分配或倍增。内存耗尽和长度溢出沿用原 x*
分配器的 fatal/诊断约定；没有返回缺项成功、静默回退或新重试。并发导出各自拥有快照，
额外内存会随同时导出数量增长，本项不引入新的导出队列或并发限额。

## 测量

Windows 本机合成语料包含中文、引号、换行与四引擎标签；目标值大小为 256/1024 字节，
按完整语料单元重复，因此实际长度略高于目标。每个组合用独立进程预热 3 次、取 30 个样本；
新旧方案交替运行 3 组，每版每场景 90 个样本，合计 1440 个测量样本。
写者更新同一个已存在的键，测量不含磁盘持久化和 HTTP；后两层由单独契约验证。
基准运行时没有同时运行完整构建。时间不是自动化门禁阈值。

## 回归与验证

新增 cache_export_tests.c 源链接完整真实缓存实现，只在测试编译单元包装 JSON 编码边界。
编码暂停时让独立线程完成一批真实持久化覆盖，再插入 4096 个键触发 rehash；
要求导出原来的完整四项、原字节和计数，写者完成且重读 TSV 得到新值。
同时覆盖空表、已有输出前缀、确切 JSON 转义和四引擎 Unicode/标签。
旧实现明确失败两项锁外编码守卫；新实现 34 项通过。

run_cache_export_tests.ps1 已接入 build_native.bat；可选 -Benchmark 生成每个样本的 JSON。
run_contract_tests.ps1 对 C/C# 两版新增完整 dump/entries 集合比对：
计数、唯一键、标签、控制字符和 Unicode 必须一致，不依赖哈希桶顺序。
