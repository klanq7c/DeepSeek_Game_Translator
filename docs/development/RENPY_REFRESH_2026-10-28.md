# Ren'Py 按完成键刷新 Text

日期：2026-10-28。范围：Ren'Py hook 及其最近守卫；共享服务协议、缓存键和其他引擎运行时不变。本文记录开发复现与验证，不是发行说明。

## 问题与失败守卫

原 worker 只报告“存在完成结果”，主线程使登记的所有 Text 布局失效并重启交互。多个完成已经合并，因此重复调度不是本次无关布局的原因。

真实 Ren'Py 7.8.7、8.1.1 的隔离项目均复现：一个迟到译文到达时，101 个无关 Text 全部被标脏。集合包含一个已有缓存命中的英文对象和 100 个中文对象，均先完成真实分词；守卫同时检查相关对象及时更新。失败日志记录的是无关布局失效数量，不是场景遍历量或帧耗时。

## 实施

1. 缓存轮询与 live worker 将还原成功的原文键交给现有主线程调度；miss、透传和令牌拒绝不成为完成键。锁保护完成键合并和取走，刷新期间到达的新键留在下一轮。
2. 真实 `Text.update` 执行期间，线程局部栈收集 `_ds_fetch` 的实际查询键。依赖来自引擎处理后的插值和自定义标签正文，不重新解释游戏表达式；嵌套 Text 各自收集。成功更新替换旧依赖，更新异常传播且栈必然退出。
3. 主线程用完成键匹配弱键依赖表，只使已捕获的相关 Text 失效。既无匹配也无保守目标时不重启交互；有目标时保留既有一次重启。
4. 引擎 `_copy` 继承已知依赖，覆盖历史快照等正常复制。状态恢复或第三方复制产生的未登记干净对象，在首次交互时只重建自身，并记录限流诊断。对象和存档状态不增加依赖字段；弱键登记不会保留对象。
5. 复查新增插件继承 Text、重写 `update` 并使用真实引擎标签处理器的守卫，确认初版会漏刷。此类对象的查询不能由基础分词捕获，因此保留构造入口的独立弱集合：未捕获的干净对象保持原有保守刷新并记录诊断，待分词的脏对象沿用下一次绘制。标准对象捕获成功后退出该集合。

## 范围与代价

本次减少已捕获对象的无关布局失效，并未建立可见场景索引。每轮仍遍历存活依赖及未捕获弱集合，匹配键的隐藏或历史对象也可能刷新；存在目标时，交互重启仍可能使屏幕执行原有更新流程。插件保守刷新继续存在。每次实际分词增加一次查询键收集，依赖键随 Text 生命周期释放。

不迁移缓存，不追加远端请求，不改写游戏文件或用户存档。游戏原有的 Text 更新、插值、标签处理和语言切换仍由引擎执行。

## 验证

- 修复前两版真实引擎的新增守卫均失败，101 个无关对象被标脏。
- 修复后同一守卫均为 0；相关对象仍显示迟到译文。
- 专项 Python 守卫 39 项通过，包含原有缓存寿命与迟到 queued 结果保护、旧版主线程回调、现代完成合并、新结果在刷新期间到达、派发异常后保留完成键供下一次通知处理、无匹配不重启、两种弱登记释放、嵌套捕获及引擎异常后的栈清理。两个真实 worker 的通知分别执行生产函数，仅通过有效还原键。
- Ren'Py 7.8.7 与 8.1.1 均运行原始 hook 和真实 Text：源码与仅原 `.rpyc` 两轮结果一致，原 `.rpyc` 字节不变；包含动态 scope、历史快照、Text 状态恢复、嵌套自定义标签、热缓存源键、旧键移除和 60 帧样式变化。7.8.7 使用旧版主线程回调，8.1.1 使用主线程派发接口。
- 最终配置 Ren'Py 7.8.7、8.1.1 及 Godot 4.3 的 payload suite 为 128 项通过；实际 Ren'Py 7.8.7 每轮 204 个断言、8.1.1 每轮 197 个断言，源码和仅编译脚本均通过。
- 最终 `build_native.bat` 退出码 0，构建产物新鲜度检查通过；两版启动器重新嵌入当前 hook，部署守卫确认 Ren'Py hook 与当前源码字节相同。启动器一致性 284 通过/0 失败；构建内的 Unity、共享核心、持久化故障注入、响应缓冲、模型配置、服务边界及四引擎审计门禁均正常结束。运行时源码在最终构建启动后未再修改，后续只补充线程派发失败的断言和文档。
- `git -c core.whitespace=cr-at-eol diff --check` 通过。本轮未额外运行完整 `run_contract_tests.ps1`；共享服务源码和 HTTP 字段未因本次刷新优化变更，构建内已有的服务边界守卫仍执行。

最初配置 Godot 3.6 的 payload suite 未通过：场景守卫打印 `SCENE_REFRESH_PASS` 后，进程以 `0xc0000005` 退出。独立运行该引擎 `--help`，未加载项目或翻译 hook，也复现相同退出码；Windows Application Error 记录均指向 `wintab32.dll` 的相同故障偏移。带 WinInk 选项的帮助命令也复现。此环境故障保留失败记录，未忽略进程退出码、未放宽断言、未修改系统驱动；Godot 3 的实际运行时检查在本轮属于受阻项。重新配置仅运行可用引擎不代表双 Godot 运行时全部通过。

Text 状态恢复守卫使用引擎 `__getstate__` / `__setstate__` 边界，历史快照使用实际 `_in_current_store`；不把它们写成完整游戏的读档/rollback 游玩证明。没有调用真实 provider，也没有商业游戏 profiling 或 FPS 测量。

原始日志保留在本地 `.scratch/renpy-refresh-2026-10-28/`：两个 `before-*` 为原始全量失效失败，`plugin-before.log` 为初版插件漏刷失败；两个 `after-*`、`focused.log` 为最终专项。`payload.log` 为包含 Godot 3 的中断，`godot-scene-diagnostic.log`、`godot3-control.json`、`godot3-crash-events.json` 为其诊断；`payload-final.log` / `.exit` 为可用引擎配置的最终套件。`build.log` 是插件守卫修复前的构建，最终验收以 `build-final.log` / `.exit` 为准。构建使用独立短临时目录，不运行会中断现有服务的 `-ServerSmoke`。
