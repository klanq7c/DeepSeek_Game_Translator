# Unity Mono 可选深预取预算（2026-11-06）

## 决定与范围

将可选深预取的 260 个对象预算改为“检查条目数”，包括已经扫描、为空和不活跃的条目。
TextAsset、ScriptableObject、MonoBehaviour 分别保留游标，并轮换首先扫描的类别，
防止前一类持续占满预算。默认继续关闭，80 条候选文本上限、实时任务避让、
节能模式、扫描间隔、排队优先级和原有文本筛选保持原有行为。

影响范围为 **Unity Mono / BepInEx 5 和 6**。IL2CPP、启动器、服务器、Ren'Py、
RPG Maker 与 Godot 运行代码未修改。不改用户配置、翻译记忆或游戏文件。

## 可复现证据

回归从生产源抽取收集、去重标记、字符串提取、tick 门禁和异步排队方法；
新窗口直接源链接。Unity 对象发现、配置、时钟、网络及候选文本筛选使用受控替身。
因此这些数字衡量实际收集循环的访问次数，不代表 Unity 原生发现耗时、候选文本
语义质量或游戏帧率。

| 合成场景 | 发现条目数（前 / 后） | 单轮检查数（前 / 后） | 新处理数（前 / 后） |
| --- | ---: | ---: | ---: |
| 1 万个已经扫描的 TextAsset | 10000 / 10000 | 10000 / 260 | 0 / 0 |
| 1 万个不活跃 MonoBehaviour | 10000 / 10000 | 10000 / 260 | 0 / 0 |
| 1 万个空条目 | 10000 / 10000 | 10000 / 260 | 0 / 0 |
| 1000 个各产出一条文本的 TextAsset | 1000 / 1000 | 80 / 80 | 80 / 80 |
| 100 个无文本对象，预算设为 7 | 100 / 100 | 7 / 7 | 7 / 7 |

修复前守卫出现 **8 个预期失败**：三种超预算场景、重复扫描的预算、
共享类别预算、类别饥饿和两个零预算边界。其余已有守卫继续通过。
修复后这些反例全部通过，另外覆盖以下行为：

- 已扫描的 9999 项前缀后有一个新对象：每轮检查不超过 260 项，第 39 轮到达尾部。
- TextAsset 数量很大时，三轮内 ScriptableObject 与 MonoBehaviour 也能得到检查。
- 模拟已扫描集合超过 4096 后清空，游标仍向后推进；39 轮覆盖稳定数组的 1 万个对象。
- 场景重置恢复类别与对象游标起点；数组缩小、组件由不活跃转为活跃仍可处理。
- 默认关闭、节能模式、实时工作繁忙、已有 worker 和扫描间隔均阻止不适当扫描。
- 扫描属性异常有诊断并释放 active 标记；worker 保持 16 条批次和原有 dialogue
  优先级，遇到实时任务或关闭配置时保留队列余项，成功或异常结束均释放 active 标记。

## 实现与取舍

[DeepPrefetchScanWindow.cs](../../payloads/UnityTranslator/src/DeepPrefetchScanWindow.cs)
只保留三个整数位置和下一个类别，不保存 Unity 对象数组或对象引用。
调用方每轮按需重新发现当前类别，窗口使包括空项在内的每次访问都消耗预算。
扫描可以由文本上限提前停止；下一轮从各类别上次检查的位置继续。

[DeepSeekTranslator.cs](../../payloads/UnityTranslator/src/DeepSeekTranslator.cs)
在场景状态重置时清空窗口；现有容量回收只清空已扫描集合，不重置窗口。
调试日志将发现、检查、新处理与入队文本分别列出；没有新增吞异常的后备路径。

限制与代价：

- 每次调用 Unity 发现 API 仍会枚举整类对象；游标不能消除这部分时间或分配。
  发现计数统计 API 返回的条目，未测量 Unity 内部遍历；初始化也未计入该夹具。
- 新对象在长前缀后会更晚得到预取。上述尾部场景从原来一次大扫描变成 39 轮；
  按现有两秒间隔，理想情况下从第一轮到尾部约需 76 秒，实时任务避让可能更久。
  实时文本翻译仍走原通道。该取舍用于默认关闭的后台功能，不承诺首屏加速。
- 稳定枚举顺序下可保证逐步覆盖；引擎持续增删或重排对象时，不承诺固定轮数内覆盖。
- 预算限制条目数，不是耗时。一项对象的反射字段、长字符串拆分仍可能有较高成本。
- 文本去重集合与对象去重集合原有容量回收策略保留；没有引入跨场景缓存或改变
  候选文本筛选、标签、共享译文和持久化规则。
