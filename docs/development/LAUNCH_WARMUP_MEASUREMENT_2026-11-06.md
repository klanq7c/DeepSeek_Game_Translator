# 0.4.1.1 启动前预热测量与决定（2026-11-06）

## 结论与范围

完成优化审查“先测量再决定”候选第 2 项：Unity / RPG Maker 启动前预热。
本轮保留现有流程，没有把扫描或队列提交挪到游戏启动后。新增可重复的测量工具及记录；
未修改生产启动器、引擎 payload、服务端、版本、游戏或配置。

测量证明预热会延后启动边界，且批次确认等待可能超过扫描；但不构成无条件后台化的依据。
Unity 既有译文导入与 XUnity 文件回填必须先于插件读取。资源文本若在预热期间完成翻译，
也会增加启动时的缓存命中。原要求是保持既有行为，不能只优化启动时间而默认牺牲这一点。

下一步仍按原清单推进 Unity Mono 可选深预取预算。这里的测量候选已完成评估；
启动后扫描没有实施，也没有被标作完成。

## 当前调用链

- C 的 run_engine_launch_flow 和 C# 的 LaunchFlow.RunEngineLaunchFlow 对 Unity /
  RPG Maker 都先执行预热，再进入游戏启动边界；外层工作线程保证窗口消息不被阻塞。
- Unity 先读 XUnity 翻译文件。空值查询本地缓存，命中后按原换行/转义回填并保留备份。
  随后扫描资源，在服务就绪后导入已有译文，再提交预热批次。翻译文件中未命中的窗口
  本来还会提前提交 prefetch，这些请求副作用没有被测量器删掉。
- 已有译文导入上限是 **1200**，资源采集上限是 **8000**，两者不同。
  大型夹具实际导入 1200 项并输出上限诊断；没有提高上限来制造测量通过。
- RPG Maker 先扫描插件参数、外部文本与数据库 JSON，再提交预热，采集上限 40000。
- Ren'Py / Godot 的既有先启动路径不属于本项测量；原有后台行为保持。

## 可复现方法

工具：tests/launcher_parity/measure_launch_warmup.py。

```powershell
python tests/launcher_parity/measure_launch_warmup.py --rounds 5
```

默认创建唯一临时目录；也可传 --output 指定尚不存在的目录。已有目录会拒绝，不清理历史文件。
结果、生成探针和夹具全部保留。工具是手动性能测量入口，不增加机器速度门禁。

- C 探针复制真实 warmup.c 并源链接其他生产扫描/文件模块，提取 ui.c 中完整的引擎启动流程。
  只在阶段边界计时、把本地 HTTP 端口指向自有服务，并将实际进程创建替换为启动事件。
- C# 探针编译当前完整启动器与共享核心源码，使用原有 SpawnSink 演练接口。
  Warmup 的三个 HTTP 基址都替换为自有动态端口，构建前断言固定地址已全部移除。
  不改变协议、解析、过滤、采集容量、导入、回填或批次控制流。
- 每次测量是新进程；计时从实际引擎流程入口到演练启动事件，不包含进程创建、
  部署或本地服务器启动。包括阶段首次调用及 C# JIT 成本。
- 每组 5 次，共 2 个引擎 × 2 个规模 × 4 个服务条件 × 2 个实现 × 5 = **160 次**。
  磁盘文件在哈希检查时已读过，属于热文件缓存测量，没有清空系统缓存或测量冷盘启动。
- 假服务条件：预热只入队；资源已有缓存；每个批次在应答前立即产生固定译文；
  只入队且每次 POST 增加 5 ms 确认延迟。最后一种延迟是受控输入，不是生产重试或掩盖竞态。
  不访问远程提供商，不用它推断真实模型吞吐量。
- 每次验证原资源哈希、XUnity 回填的精确文件字节及备份、导入上限、采集键集合、
  预热先于启动，以及 C/C# 所有请求顺序、解析内容和原始正文 SHA-256 完全一致。

探针开发初期暴露了三处夹具问题：C# 缓存查询分支的端口替换遗漏、导入上限误按资源数量计算、
RPG Maker 夹具漏了 js/main.js。前两轮错误探针曾向默认端口尝试只读缓存查询；未进行启停或
配置变更。修正了探针端口覆盖与夹具预期/标记文件，增加静态地址检查；正式 160 次全部通过。
这些失败不计入最终结果，也没有改动产品逻辑来迎合夹具。

## 启动边界缓存可用性

这部分是预先指定文本的缓存查询结果，不是游戏实际绘制或完整首屏验证。
Unity 样本包含 50 个已有译文键、50 个空行回填键和 50 个资源键；RPG Maker 为 50 个资源键。

| 服务条件 | Unity，启动前初始 → 当前流程启动边界 | RPG Maker，启动前初始 → 当前流程启动边界 |
| --- | --- | --- |
| 只入队，无新增译文 | 50/150 → 100/150 | 0/50 → 0/50 |
| 资源预先有缓存 | 100/150 → 150/150 | 50/50 → 50/50 |
| 每批应答前产生译文 | 50/150 → 150/150 | 0/50 → 50/50 |

只入队不能保证首屏译完；但最后一组是反例：当前流程确实允许资源译文先于启动可用。
把启动无条件移到资源扫描前，在相同初始状态的启动瞬间拿不到这些新增结果。
保留导入前置只能保护已有译文，不能自动保护全部资源文本的首屏命中。

本项没有在真实游戏中对比首屏，也没有实施扫描与游戏资源加载并发，因此不声称已验证
资源读取竞争。背景扫描需要额外的选择策略、首屏验证和文件并发所有权证据，目前不足以
替换默认流程。此次保留现状是测量后的决定，不是测试失败或未完成测量。
