# HTTP 分片测量与增量解析（2026-11-06）

## 结论与范围

对本地 C/C# 服务的请求收包层实施增量头部边界查找，并在头部完整后只解析一次
Content-Length。该入口由 Ren'Py、RPG Maker、Unity 和 Godot 共用，因此同时核对
两版服务、四引擎格式标记和既有缓存契约。

本项针对大量分片时的重复工作。普通 localhost 短请求一次收齐时没有明显收益，
不将合成夹具的改善写成游戏帧率或日常端到端延迟承诺。

## 复现与决定

源链接生产收包循环、长度解析和分隔符查找，替换 socket 读取/发送与内存池边界。
使用相同字节和分片大小运行旧/新实现，核对状态、正文长度和 FNV-1a 字节哈希。

- 128 KiB 正文按 7 字节分片：旧 C 反复解析长度 **18,727 次**，新实现 **1 次**。
- 约 32 KiB 头部按单字节分片：旧 C# 累计 ASCII 解码 **539,511,970 字节**，
  新实现只解码完整头部 **32,844 字节**。
- 94 字节短请求一次收齐：两版长度解析都仍为 1 次，属于没有重复长度解析的对照。
  C# 从解码整次读取的 94 字节，改为只解码头部的 64 字节。

初版反例产生 28 个预期工作量失败。随后将 C 正文定位也改为使用生产表达式，
最终同一夹具对旧实现产生 30 个工作量失败；对新实现为 0。
状态与正文检查在旧/新实现均通过：**116 组样例、183 项检查**。

计数含义须区分：旧 C 的 searchBytes 是 strstr 查找的逻辑范围，不是 CRT 实际
逐字节比较次数；新扫描器统计候选起点数，每个起点最多比较四字节。C# decodedBytes
是 ASCII 解码输入量，不是托管堆实测峰值。数字不包含 Unity/游戏运行时。

## 实现

- [http.c](../../native/src/server/http.c) 的 find_header_end 只检查上次不足四字节的
  后缀和新增数据。头部完成后保存长度与总请求长度，接收正文时不再重新解析头部。
  头部、正文均通过偏移定位，缓冲扩容不会留下旧指针。
- [HttpRequestFraming.cs](../../native/src/core/HttpRequestFraming.cs) 提供同样的增量
  分隔符扫描；[Program.cs](../../native/src/server_cs/Program.cs) 在找到完整头部后
  才进行 ASCII 解码，后续请求行解析复用该字符串。
- 2 MiB 上限仍包括头部和正文；原有溢出、重复长度、正文不足、断开、五秒接收超时、
  Origin 与超时缓冲不得回池的处理保持原判定。没有增加等待、重试或吞异常的后备路径。
- 保留原有每种语言的畸形输入语义。例：包含内嵌 NUL 的合成头部，旧 C 停止字符串
  查找并最终报 400，旧 C# 可继续解析；本次分别保持原行为，没有借优化改写协议策略。

## 测量边界

定时夹具使用 Release 优化、受控内存分片，C# 预先执行一次以排除首次 JIT，
并将正文哈希检查包含在每次运行中。五组重复交替运行旧/新实现，每组短请求
3000 次、分片正文 10 次、单字节长头部 3 次、一次收齐长头部 10 次，记录中位数
及范围。最终数据在构建完成后单独重测，原始样本保留在本地。

这里没有 TCP 调度、provider 延迟或游戏绘制，因此主要采用确定性工作量约束。
一次收齐的长头部在 C 中可能因显式扫描而稍慢；这是减少极端分片重复扫描的取舍。

构建结束后的五组中位数如下，单位为毫秒；这些是带计数、内存读取和正文哈希的
夹具时间，不能当作生产 HTTP 请求端到端时间：

| 场景 | C：旧 → 新 | C#：旧 → 新 |
| --- | ---: | ---: |
| 94 字节短请求，一次读取 | 0.006111 → 0.006079 | 0.002170 → 0.002252 |
| 94 字节短请求，单字节分片 | 0.008630 → 0.006668 | 0.008155 → 0.003884 |
| 128 KiB 正文，7 字节分片 | 1.426280 → 0.279900 | 0.723790 → 0.714920 |
| 约 32 KiB 头部，单字节分片 | 43.360933 → 0.125267 | 568.429033 → 1.082500 |
| 约 32 KiB 头部，一次读取 | 0.024440 → 0.035940 | 0.185570 → 0.153050 |

短请求一次读取的差异很小，不据此声称提速；C 长头部一次读取约多 0.012 ms。
决定保留简单有界扫描，用这点合成场景代价换取分片数增大时不重复扫描整个前缀。

## 回归与复现

~~~powershell
python tests\server_contract\http_framing\run_framing_tests.py
python tests\server_contract\http_framing\test_wire.py
~~~

两个入口均加入 build_native.bat：

- 分片夹具覆盖 1/2/3/7 字节分片、多个候选前缀、同次读取中的正文、
  128 KiB 正文、缓冲扩容、精确 2 MiB、超限、无/零/负/重复/溢出长度、
  不完整输入、额外尾随请求、内嵌 NUL，以及中文和四引擎标记。
- 实际 TCP 夹具对两版当前程序合计 **66 组**，包括断开、头部/正文超时、
  128 KiB 头部与正文扩容、精确上限、超限、Origin，以及超时后连续八次中文
  和四引擎标记查询。TCP 可以合并发送分片，精确 recv 分片由前一个夹具负责。
- 实际端口、缓存、配置和进程均由夹具拥有；测试不调用真实 provider，
  不启动或停止用户正在使用的服务，不修改游戏文件。

本轮完整构建退出码为 0，包含上述新门禁、Unity 运行契约 247/0、
启动器 C/C# 一致性 284/0 及既有其他门禁。额外的双服务 HTTP 契约为 **160/0**。
真实 TCP 修复前后 66 组的状态与错误字段逐项一致；超时后的两版服务仍能正确
查询中文和四引擎标记。最终执行完整产物校验、源码准备 -NoZip 与审计，
并逐文件核对暂存源码 SHA-256；当前程序、插件、托管指纹及日志哈希写入验证清单。

本地证据目录为 .scratch/http-framing-2026-11-06/，包括旧源副本、修复前失败日志、
baseline-final/、after/、wire-before/、定时样本、完整构建与最终 verification.json。
本项完成表示优化清单已有处理结论，不代表四引擎完整游玩验证或已经发布。
