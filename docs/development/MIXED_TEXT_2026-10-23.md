# 半汉化与中英混合文本补译（2026-10-23）

## 行为与范围

修复此前“文本只要包含汉字便整段跳过”的漏翻。现在含可见英文的混合句可进入原有异步查询和翻译通道，纯中文继续透传。标签、变量、控制码、URL、短缩写与单位不作为英文补译信号；大小写英文 UI 单词均可识别。未知专有名词是否应保留仍属于翻译质量和术语选择，字符判定不宣称理解全部语义。

影响范围包括 C/C# 服务的文字判定与提供商请求边界，Ren'Py、RPG Maker、Unity Mono/BepInEx 5/6 和 Godot 3/4 的查询/显示入口，以及 C/C# 启动器预热与 Godot 静态资源判定。Unity IL2CPP 继续沿用已有的混合中文保护和 SDK 恢复协议，共享规则通过源链接更新；短混合句也能由新服务处理。

## 中文保护与重复送译

模型收到的待译正文使用稳定 ASCII 标记代替原有连续汉字段，标记前缀避开本条原文。结果必须按原有顺序保留全部标记，每个恰好一次；恢复后原有汉字段逐字相同。丢失、重复、重排或无法恢复的结果拒绝写入成功缓存，日志记录 `mixed-cjk` 上下文，游戏继续使用原文或已有安全命中。缓存仍先查本地；`cache_only` 不等待远程 API，协议字段、原文键和现有翻译记忆没有迁移。

新增的近期已完成译文记录解决了第二层问题：安全译文可能仍保留 `John` 等英文名字，后续扫描不能把它再次当作新混合原文。记录由对应引擎管理并有容量限制；Unity 同时记住实际字体/标点兼容后的显示结果。此记录不作为新的成功翻译写回共享缓存。仍继续保留已有混合残片修复、字体兼容、颜色、变量与排队完成规则。

## 同日复查：混合文本经过后续处理的边界

此前通过的守卫未覆盖以下实际路径，本次分别复现后修复：

- 中文标记已经正确恢复，旧缓存清洗仍可能删除原文里的“翻译成简体中文：”说明文字。归一化现在感知对应原文的前缀层数，只删除模型多出的回显层；API、缓存写入/加载和 Unity Mono/IL2CPP 显示清洗使用同一规则，普通回显清理与原文等值拒收继续保留。
- Unity 生成的相邻 `__DS_TOKEN_0__Continue__DS_TOKEN_1__` 被 C# 贪婪匹配成一个标记；URL 后的全角标点也可能与后续英文一起被当作路径。标记改为第一个闭合边界，URL 在可打印 ASCII 字符结束处终止，C/C# 和脚本判定对齐。
- RPG Maker 的 `Bitmap.drawText` 入口仍把所有含汉字的文本跳过；现在与菜单路径共用混合文本判定，覆盖冷缓存查询和暖缓存恢复。URL 字段不能成为旧“连续英文残留”检查里的普通单词。
- Ren'Py 的 `[[`、`{{` 是字面括号，尖括号和下划线也是普通内容。钩子复用自身真实标签/插值 span，`/batch` 与 `/prefetch` 携带可选 `engine: "renpy"`；两版服务在准入时使用该引擎的可见性规则，原文缓存键保持不变。启动器的 Ren'Py 扫描和预热请求也同步该语义，C# 字节串先解码再按 Unicode 码点判断变量长度。缺省或未知引擎提示仍按原通用规则，不改变其他引擎自定义标签的判定。
- 已完成译文仍含英文人名时，颜色格式变化不应重新补译。Unity 与 Ren'Py 以去真实格式标签后的显示正文记录完成，Godot 按实际写回的已完成文本槽记录，未命中相邻项继续发现。真实空白、换行及 Ren'Py 字面括号保留，格式清洗原文本身不记作成功。
- Unity 旧令牌占比过滤会拒绝 `请 <color=red>Save</color>` 等短混合词；有可见英文实词时放行，真正短碎片继续过滤。补译未命中/排队期间，原有汉字继续准备 TMP/UGUI/IMGUI 字体兼容；这些显示准备不能把原文误记为成功译文。
