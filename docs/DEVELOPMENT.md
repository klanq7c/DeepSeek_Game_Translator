# 开发与发布约定

本文面向开发者及参与项目的 AI。进行开发、验证、清理或发布前应阅读本文件，
并遵守根目录 [AGENTS.md](../AGENTS.md)。项目领域说明见
[CONTEXT.md](../CONTEXT.md)，代码与测试入口见 [维护索引](MAINTENANCE_MAP.md)。

## 一、文档放在哪里

| 内容 | 位置 | 写作要求 |
| --- | --- | --- |
| 玩家关心的功能变化、修复和升级方法 | README 顶部更新日志、`docs/UPDATE_日期.md`、GitHub Release | 用中文说明实际变化，保持各处一致 |
| 项目名称、支持的引擎、主要用途 | GitHub About | 概述当前能力，避免写死版本号；下载入口使用 `/releases/latest` |
| 开发流程、发布要求和长期约定 | 本文件、AGENTS.md、维护索引 | 发生流程遗漏时在对应规则中补齐 |
| 可公开的验证摘要、复现与修复结论、验证边界 | `docs/development/` | 标明版本或提交及日期；删除密钥、真实游戏文本和本机路径 |
| 原始日志、诊断输出、临时探针和本机操作记录 | `.scratch/<任务>/` | 保留必要诊断，不加入 Git 或玩家下载包 |

玩家更新日志和 About 不放“已完成验证”、测试数量、内部验收过程或调试输出。
测试仍须执行，结果写入开发记录。玩家需要知道的兼容范围、安装要求及已知功能限制
仍应在使用说明中准确告知。

开发文档随源码维护；程序 ZIP 的文档面向玩家，不追加整份开发报告。

## 二、开发与回归

1. 先确定影响范围：共享服务器/API/缓存、启动器、Ren'Py、RPG Maker、
   Unity Mono/BepInEx 5/6、Unity IL2CPP/XUnity/TMP 或 Godot。
2. 改共享逻辑前检查所有调用路径；引擎显示问题留在对应适配层，不改写共享译文。
3. C 启动器与 C# 镜像同步修改；新增嵌入资源同时登记两边的资源清单。
4. 可复现的缺陷补充最近的回归守卫；部署、预热、缓存、标签、字体、并发和持久化
   改动同时保护相邻引擎或共享契约。
5. 按 AGENTS.md 的验证要求运行检查，报告失败和跳过原因，不删除或放宽失败断言。
   自动检查结果不能写成“所有游戏无 bug”或完整游玩结论。
6. 说明性代码注释使用中文；技术标识、协议字段、第三方版权与许可原文保持原样。

常用验证入口：

- `build_native.bat`：完整构建及其内置回归门禁。
- `tests/server_contract/run_contract_tests.ps1`：C/C# 两版服务契约。
- `tests/payload_scripts/check_payload_scripts.ps1`：脚本及已配置的实际引擎夹具。
- `tests/launcher_parity/run_launcher_parity.ps1 -ServerSmoke`：真实服务生命周期；
  必须先确认端口 19999 空闲，不能中断用户正在进行的翻译。
- 界面布局或绘制修改：一致性探针之外，检查真实窗口和当前 DPI 下的画面。

仅修改说明文档时检查内容、链接及发布内容一致性，不重复完整构建。

## 三、发布完成的标准

用户要求发布这版更新或更新 GitHub 程序时，应完成可下载程序的发布。
仅推送源码、创建 PR 或生成本地 EXE 都不能记作已经发布程序。
用户明确限定“只推源码”“只建草稿”或“暂不发布”时，按其指定范围执行。

### 准备

- [ ] 核对工作区、远端分支、现有 Release 和本次改动范围。
- [ ] 有程序更新时更新 `VERSION`，重新构建，确认 EXE 元数据、页脚、
  C# 编译信息与 Godot 预检版本一致；不要只改文件名冒充新版。
- [ ] 完成影响范围所需的验证，将结果写入开发记录。
- [ ] README 顶部放最新更新，更新使用说明中的当前版本和下载文件名。
- [ ] `docs/UPDATE_日期.md` 与 Release 使用同一份面向玩家的更新内容。

### 打包

运行以下脚本，版本默认从 `VERSION` 读取：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\prepare_program_release.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\prepare_open_source_release.ps1
```

- [ ] 单文件启动器：`ds-translator_<版本>.exe`。
- [ ] 程序包：`ds-translator_<版本>.zip`，包内保留 `ds游戏翻译器.exe`。
- [ ] 源码包：`DeepSeek_Game_Translator_source_<版本>.zip`。
- [ ] `SHA256SUMS.txt`：记录上述三个文件的实际 SHA-256，文件变化后重新生成。
- [ ] 程序包包含 README 引用的更新日志、使用说明、字体许可和指纹清单；
  打包脚本内的实际 ZIP 检查及空目录资源释放检查通过。
- [ ] 源码包通过发布审计；不得夹带真实配置、翻译记忆、日志、游戏文件或未获准分发的依赖。

下载附件使用稳定的 ASCII 文件名，避免 GitHub 将中文名称改成 `ds._…`。
程序 ZIP 和单文件版必须对应同一份构建。详细发布边界见
[源码发布检查表](../OPEN_SOURCE_RELEASE.md)和[依赖政策](DEPENDENCY_POLICY.md)。

### GitHub 同步

- [ ] 将本次源码及文档推送到正确分支；需要合并时确认主分支包含待发布代码。
- [ ] 为实际发布提交创建版本标签，将三个下载文件和校验清单上传到对应 Release。
- [ ] 检查 Release 已公开，并按发布意图设为最新版；草稿不可作为已完成下载交付。
- [ ] 检查 About 简介包含当前支持的 Ren'Py、RPG Maker、Unity 和 Godot，
  没有遗留旧产品名称或版本号；topics 同步引擎范围，保留其他有效主题。
- [ ] About 的主页链接指向本仓库 `/releases/latest`。
- [ ] README 下载链接、Release 附件名和升级说明一致。
- [ ] README 标题下及 Release 正文开头提供唯一的“新用户推荐下载”EXE 直链，
  明确下载后双击运行；不能只给发布页链接，让新用户自己辨认附件。
- [ ] 附件显示名称使用用途说明：EXE 标为“推荐下载”并显示 `.exe`；ZIP 标为
  “备用下载，解压后运行”，说明与 EXE 功能相同、二选一；源码标为“开发者专用”，
  校验文件标为“可选”。不要把所有附件统称为“推荐下载”。
- [ ] 下载说明明确 GitHub 自动附加的两个 `Source code` 是源码，普通使用无需下载；
  核对实际附件 label，不能只改正文。保留已发布的稳定文件名和下载地址。
- [ ] 读取 GitHub 返回的附件大小与 SHA-256，与本地文件核对；返回值不提供哈希时，
  下载对应附件核对。上传失败后先检查已有附件，避免重复创建发布项。
- [ ] 最后向用户给出可用下载链接；如有未完成步骤，明确说明，不笼统称“已发布”。

## 四、发布后的文档修正

修改当前版本的玩家说明时，同步 README、`docs/UPDATE_日期.md`、Release 正文和
相关 PR 正文；下载 ZIP 内有同一份说明的，也要重新打包并更新附件及校验清单。
核对程序字节没有被文档修改意外改变。历史发布标签不强制重指向新提交。

仅新增开发流程或开发记录时，更新源码仓库即可；不为此改版本号或重新发布程序。

## 五、清理边界

- 清理范围以用户授权为准。保留可运行程序、插件、源码、配置、翻译记忆和构建依赖。
- 删除前检查实际依赖；某些 `bin` 目录可能是 Unity 编译引用的唯一来源，不能只凭名称删除。
- 检查绝对路径与链接，避免递归操作越出预定目录。
- 自动审批拒绝时如实记录被拒绝的操作及返回原因，不能把未执行的删除报告成已完成。
- 用户已要求移除清理脚本时，不再自行增加同类脚本。
